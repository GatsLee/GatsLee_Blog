# 3-Layer RAG 검색 구현기: 제목에서 임베딩까지

**카테고리:** devlog
**태그:** RAG, search, embeddings, SSE, Next.js
**프로젝트:** one-by-one-cs

---

## 요약

CS 학습 플랫폼에 3단계 검색을 구현했습니다. 정확한 매칭부터 시맨틱 검색까지, 각 레이어가 이전 레이어를 보완하는 구조입니다.

---

## 임베딩만으로는 아쉬웠다

71개의 MDX 문서에서 원하는 내용을 찾는 검색이 필요했습니다. 처음에는 임베딩 검색만 넣었는데, "운영체제 스케줄링"같은 정확한 쿼리에서 오히려 느리고 부정확했습니다. 제목에 딱 있는 내용인데 임베딩 유사도 순위에서 밀리는 경우가 많았습니다.

## 3개 레이어

결국 세 단계로 나눴습니다.

**Layer 1 - 제목 정규화 매칭**

`normalizeQuery()` 함수로 한국어 질문 접미사를 제거합니다. "운영체제 스케줄링이 뭐야?", "스케줄링에 대해 알려줘" 같은 질문에서 핵심 키워드를 추출한 뒤 문서 제목과 매칭합니다. 가장 빠르고 정확합니다.

**Layer 2 - 태그 키워드 매칭**

각 문서에 20-30개의 태그를 미리 생성해뒀습니다 (인덱싱 시점). 메모리에서 키워드를 매칭합니다. Layer 1에서 놓친 연관 문서를 잡아줍니다. 예를 들어 "프로세스"를 검색하면 제목에는 없지만 태그에 포함된 "컨텍스트 스위칭" 문서도 나옵니다.

**Layer 3 - 임베딩 RAG**

Ollama로 쿼리를 임베딩하고 ChromaDB에서 유사도 검색합니다. 가장 느리지만, "컴퓨터가 여러 작업을 동시에 하는 방법"같은 자연어 질문에 효과적입니다.

## 중복 제거

`seenFilePaths` Set으로 레이어 간 중복을 방지했습니다. Layer 1에서 이미 나온 문서는 Layer 2, 3에서 제외됩니다. 사용자가 같은 문서를 두 번 보는 일이 없습니다.

## SSE 스트리밍

결과가 레이어별로 도착하는 대로 클라이언트에 전송합니다. 이벤트 타입을 나눠서 UI에서 구분할 수 있게 했습니다.

- `title_match`: Layer 1 결과 (거의 즉시)
- `tag_match`: Layer 2 결과 (수십 ms)
- `result`: Layer 3 결과 (수백 ms)
- `rag_answer`: LLM이 생성한 요약 답변

사용자는 첫 번째 결과를 거의 즉시 보고, 나머지는 점진적으로 채워지는 경험을 합니다.

## 배운 점

- 가장 단순한 매칭을 먼저 시도해야 사용자 체감 속도가 빨라졌습니다
- 태그를 문서 작성 시 자동 생성하면 유지보수 부담이 거의 없었습니다
- SSE는 WebSocket보다 구현이 간단하고, 이런 단방향 스트리밍 용도에는 충분했습니다
