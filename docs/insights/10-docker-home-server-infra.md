# Docker 기반 홈 서버 인프라 구축기

**카테고리:** devlog
**태그:** Docker, MariaDB, Nginx, Prometheus, Grafana, self-hosting
**프로젝트:** docker/infrastructure

---

## 요약

블로그, 에이전트, 모니터링 서비스를 모두 Docker Compose로 운영하는 홈 서버 인프라를 구축했습니다.

---

## 클라우드 비용 없이 모든 걸 돌리고 싶었다

프로젝트가 늘어날수록 서비스도 늘어났습니다. 블로그, 에이전트 3개, 모니터링, 워크플로우 자동화... 각각 클라우드에 올리면 비용이 금방 불어납니다. 집에 서버가 있으니 전부 셀프호스팅하기로 했습니다.

## 전체 구조

```
Nginx Proxy Manager (80/443)
  ├── blog.gatslee.com → blog:3001
  ├── agents API → orchestrator:8000
  └── monitoring → grafana:3000

MariaDB (공유 데이터베이스)
  ├── n8n 워크플로우 데이터
  └── 인프라 설정

Prometheus + Node Exporter → Grafana
Portainer (Docker 관리 UI)
```

## 네트워크 분리

Docker 네트워크를 두 개로 나눴습니다.

- **infra-net**: 내부 전용. MariaDB, Prometheus, Grafana가 여기에 있습니다
- **proxy-net**: 외부 노출용. Nginx에서 각 서비스로 라우팅합니다

에이전트가 데이터베이스에 직접 접근하지 못하게 네트워크 수준에서 격리했습니다. 간단하지만 효과적인 보안 레이어입니다.

## SSL 자동화

Nginx Proxy Manager에 Let's Encrypt를 연동했습니다. 웹 UI에서 도메인을 추가하고 "Force SSL" 버튼을 누르면 인증서가 자동 발급됩니다. 갱신도 자동입니다.

셀프호스팅의 가장 큰 진입장벽 중 하나가 SSL인데, 이걸로 거의 제로 코스트로 해결되었습니다.

## 모니터링

Node Exporter가 호스트 메트릭(CPU, 메모리, 디스크, 네트워크)을 수집하고, Prometheus가 저장하고, Grafana가 시각화합니다.

에이전트가 리소스를 과도하게 사용하거나 디스크가 차기 시작하면 대시보드에서 바로 보입니다. 서버를 운영하면서 "지금 상태가 어떤지" 모르는 게 가장 불안했는데, Grafana 하나로 그 불안이 사라졌습니다.

## MariaDB 공유 전략

여러 서비스가 각각 DB를 들고 있으면 관리 포인트가 늘어납니다. MariaDB 하나를 공유하고 데이터베이스(스키마)를 나누는 방식을 택했습니다.

백업도 한 곳에서 하면 되고, 모니터링도 한 인스턴스만 보면 됩니다. 서비스 규모가 작을 때는 이 방식이 훨씬 효율적이었습니다.

## Portainer의 가치

처음에는 "Docker CLI로 충분하지 않나"라고 생각했습니다. 하지만 Portainer를 넣고 나서 SSH 접속 빈도가 확 줄었습니다. 컨테이너 로그 확인, 재시작, 환경변수 수정 — 웹 UI에서 클릭 몇 번이면 끝납니다.

특히 외출 중에 폰으로 서버 상태를 확인하고 컨테이너를 재시작할 수 있는 게 큰 장점이었습니다.

## 배운 점

- Docker 네트워크 분리는 별도의 방화벽 없이도 서비스 간 접근을 제한하는 가장 쉬운 방법이었습니다
- 작은 규모에서는 DB를 하나로 합치는 게 관리 포인트를 줄여주었습니다
- 모니터링은 "문제가 생겼을 때" 보는 게 아니라 "평소에" 보는 것이었습니다. 정상 상태의 기준선을 알아야 이상을 감지할 수 있었습니다
