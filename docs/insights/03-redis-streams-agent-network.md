# Redis Streams로 에이전트 네트워크 만들기

**카테고리:** devlog
**태그:** agents, Redis, event-driven, orchestration, FastAPI
**프로젝트:** agents/00-orchestrator

---

## 요약

독립적으로 돌아가는 에이전트들을 Redis Streams 이벤트 버스로 연결하고, 오케스트레이터가 메시지를 라우팅하는 구조를 만들었습니다.

---

## 에이전트가 여러 개가 되면

에이전트 하나를 만드는 건 어렵지 않습니다. 문제는 여러 에이전트가 서로 협력해야 할 때입니다. 블로그 에이전트가 초안을 생성하면 AIOps 에이전트가 빌드 상태를 확인하고, 오케스트레이터가 전체 흐름을 조율해야 합니다.

처음에는 HTTP 직접 호출을 고려했습니다. 하지만 에이전트가 추가될 때마다 호출 관계가 복잡해지고, 한 에이전트가 죽으면 연쇄적으로 문제가 퍼집니다.

## 왜 Redis Streams인가

RabbitMQ나 Kafka는 이 규모에 과했습니다. Redis는 이미 인프라에 있었고, Streams 기능이 딱 필요한 만큼을 제공했습니다.

- XADD/XREAD로 pub/sub이 됩니다
- Consumer Group으로 메시지를 여러 소비자에게 분배할 수 있습니다
- 메시지가 영속적으로 저장되어서 에이전트가 재시작해도 놓친 이벤트를 따라잡을 수 있습니다

## 이벤트 스키마

모든 에이전트가 같은 형식으로 이벤트를 발행합니다.

```python
class AgentEvent(BaseModel):
    source: str       # "blog-agent"
    type: str         # "draft.generated"
    payload: dict     # {"post_id": 42, "title": "..."}
    timestamp: datetime
```

이 스키마 하나로 에이전트 간 계약이 성립합니다. 에이전트는 서로의 존재를 몰라도 되고, 이벤트 타입만 알면 됩니다.

## 오케스트레이터의 역할

오케스트레이터는 세 가지를 합니다.

1. **헬스 모니터링**: 5분마다 모든 에이전트의 `/health` 엔드포인트를 핑합니다
2. **이벤트 라우팅**: 스트림을 구독하고 라우팅 규칙에 따라 처리합니다
3. **장애 알림**: 에이전트가 응답하지 않으면 Telegram으로 알립니다

## 현재 에이전트들

- **blog-agent**: git log를 파싱해서 LLM으로 블로그 초안을 만들고 API로 게시합니다
- **aiops-agent**: Nginx/SSH 로그를 수집하고 이상 패턴을 감지해서 Telegram으로 알립니다

둘 다 FastAPI 기반 Docker 컨테이너로 돌아가고, 공유 Redis를 통해 이벤트를 주고받습니다.

## 배운 점

- 이벤트 소싱은 디버깅을 훨씬 쉽게 만들어주었습니다. 모든 이벤트가 Redis에 기록되어 있으니 문제 발생 시점을 정확히 추적할 수 있었습니다
- 에이전트를 추가할 때 기존 에이전트를 수정할 필요가 없었습니다. 새 이벤트 타입만 정의하면 되었습니다
- 헬스 모니터링은 나중에 넣으려고 미뤘다가 장애를 놓친 적이 있어서, 처음부터 넣는 게 맞았습니다
